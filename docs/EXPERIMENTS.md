# Experiment execution notes

Run each notebook in a fresh kernel with its setup cell first. Plot/export cells
depend on the results generated by previous cells. The command-line runner handles
this ordering automatically. Sources retain no stored execution output.

## Scope and result correspondence

Fig02 now loops over the configured classical iteration counts (4,10,50,200)
and unfolded depths (2,3,4), creating the output directory before saving CDFs.
It includes only the classical and unfolded curves covered by this release.
Fig04 uses the first 100 test instances for all six depths, matching its supplied
entry point. Fig06 uses the city-specific 100-instance datasets.

Fig01's former plot label said `I=4` despite a three-layer computation. The label
now says `Model-based WMMSE`; the configuration and numerical computation remain
three-layer by default.

Fig02 and Fig04 now use evaluation mode: dropout is disabled. All inference-only
evaluation cells use `torch.no_grad()`. Fig01 retains gradient-enabled training.
The evaluation-mode change can alter CDF and depth curves relative to a run with
dropout active; see the measured comparison in `VALIDATION.md`. Reference curves
in `reference_results/` are not silently replaced by new evaluation output.

## Runtime protocol

The manuscript's runtime hardware is an Apple M1 Pro MacBook Pro. Current checks
record their own platform and thread count; timings should not be interpreted
as portable constants.

The existing timing boundaries are retained. Fig03's unfolded timings start
after the GNN corrections are computed, and include optimization and hybrid
decomposition. Fig04 also times optimization and decomposition after GNN inference.
These values therefore exclude feature construction/GNN inference and are not
end-to-end application latency. Fig00 uses its original convergence and repeated
solver timing procedure. A future end-to-end timing study should be recorded as
a separate protocol and should not overwrite the manuscript reference timings.

Full notebooks can require many solver calls: Fig02 runs several algorithms on
1,000 instances, Fig05 uses six noise levels and four algorithms, and Fig06
evaluates six algorithms across four cities. Full runtimes have not been measured
during release preparation; a small smoke-check duration is not an estimate for
full training or all figures.
